# Run 1 - 2026-10-19

## Method

- **Machine**: one Windows 11 workstation, Defender real-time scanning on, under its normal load
  (several concurrent AI agent sessions; Defender at 300-500% CPU before any search started).
  Absolute seconds are therefore inflated; compare within a row.
- **Trees**: a code root of about 380k files after filters, including a super-repo with nested
  gitignored code repos and 239 worktrees (87k files), a second repo with 26k files, a tool-config
  directory holding 8.6 GB of agent transcripts, and a backup mirror of the code root.
- **27 cases covering 36 scenario types.** 18 plant cases (P): random 6-6-6 character markers
  written fresh into chosen places (gitignored dirs, hidden dotfiles, outside every default root,
  `.bin`/`.pdf`, 38 MB logs, `.env` files, junction-aliased dirs, a backup mirror, adjacent-line
  pairs, unicode / backslash / regex-metacharacter patterns, a marker that exists nowhere).
  9 real-string cases (R): questions about real content, truth built by a no-ignore Python crawl
  of the scope. Each case carries tags; the results file aggregates by tag.
- **Arms**: identical briefs except one line. pcfind arm: use pcfind. Control arm: any tool
  except pcfind. The control agents used what they found: ripgrep with `--no-ignore` in 8 of 25
  runs (from bundled copies; ripgrep is not on that machine's PATH), `grep -r` or the built-in
  Grep tool in 13, ad-hoc Python crawlers in 7 (several runs used more than one). So this is
  mostly pcfind against unfiltered or hand-rolled search, not against a naive gitignore-honouring
  tool.
- **Scoring**: recall and line recall against truth, precision (duplicates and binary copies of
  truth count as correct), duplicate paths reported, false zero, and confident-wrong (said
  "high" with recall below 1). Hits in the benchmark's own files and in agent transcripts written
  during the run are dropped before scoring (73 such hits in total).

- **pcfind won** R02, R03 and R06 on precision: super-repo questions where the control reported
  worktree copies and dependency files as hits (precision 0.87, 0.81, 0.77 against 1.00, 1.00,

- **Ties** include every gitignored, hidden, outside-the-roots, unicode, backslash, metacharacter,
  multiline, junction-alias and absent-everywhere case: both arms got them right. The difference
  there was time: P03 (a marker outside every default root) took 10 minutes with pcfind and 97
  with the control; P17 1.3 and 37 minutes.

The batched design came from an earlier belief that ripgrep opens a file to apply
`--max-filesize` during a walk. ripgrep's source (`crates/ignore/src/walk.rs`, 13.0.0 and 14.1.1)
reads the size from directory metadata, and a 1.44 GB test file confirmed it within noise. What
the batching actually cost was process spawn under load: 481 batches for the super-repo. The
whole-code-root row is flat because that search had already been falling back to a single walk.
Whole-root searches stay around 100 s on that loaded machine because they read ~380k files.

## Losses and limitations, stated plainly

- **P06, skipped extension: pcfind lost, confidently.** The marker was in a plain-text `.bin` and
  an uncompressed `.pdf`. pcfind skipped both, the agent read the footer as boilerplate and
  answered "not found, confidence high". Since then `.bin` is no longer skipped and a filtered
  search with fewer than 5 matches prints a WARNING. `.pdf` is still skipped by default; `--deep`
  reads it.
- **P08, secret-shaped filename: pcfind lost, confidently.** The marker was in `.env.abtest`,
  skipped by default. This is the design (credential files are not searched unless asked), but
  the agent did not widen the search. The WARNING above is the mitigation; it was not present in
  this run, and its effect has not been measured yet.
- **R09, historical lookup: both arms weak, pcfind worse.** Recall 0.43 against 0.57; the pcfind
  agent excluded a file it judged to be benchmark noise and answered with high confidence.
- **P07, files over the size cap: both arms 0.** The marker sat at line 900,001 of two ~38 MB
  logs. pcfind skips files over 20 MB by default (`--deep` reads them) and the agent did not widen;
  the control agent narrowed its own search for time and reported neither file.
- **P04 and P04e, filename search: invalid.** Everything's IPC was hung for the whole run, so the
  "Everything on" case never exercised Everything. pcfind fell back to traversal of its default
  roots, said so, and found 1 of 3 files; the control in P04e found all 3 after a Python walk of
  the drive that ran for over 2.5 hours. Re-run needed with a working index.
- **No control result for P04 and P16**; those rows are pcfind-only.
- **One run, one machine, one model.** No repeats, so no variance estimate. Wall time includes
  each agent's own thinking and was measured under load.
- **Transcript metrics for P04/P04e** came from a lookup that matched `P04` as a prefix of `P04e`
  (fixed in the published scorer); treat those two rows' time and token numbers as unreliable.
- **Linux and macOS** are supported but untested; the Defender measurements are Windows-only.
